# Automated decompilation loop

How the top-level Claude session runs batches of agents, each matching one function, and lands their work on `mainline`. The per-function procedure is in `.claude/skills/decomp-function/SKILL.md`; the manual version is `docs/workflow.md`.

## One batch

0. **Tools first.** Before a batch, on `mainline`, run `python3 tools/propagate.py` and `python3 tools/trivial.py` (they match functions with no model tokens; see `docs/workflow.md`). Record each run in `loop-prompts/batchN/tools.txt`: `tool | mainline before | candidates | matched | build errors | diffs >= 99% | CPU minutes | commit`.
1. **Pick.** Model work is chosen with `python3 tools/fn.py pick --families` (heads first: each head matched pays for its whole family when `propagate.py` runs afterwards). `python3 tools/fn.py pick -n 40` lists functions not yet in any file: entries in `config/AWRE/interesting.txt` first, then fewest unmatched callees, then smallest. Choose a batch (5–10 at first) and skip functions that call each other, so two agents never need the same callee renamed.
2. **Start agents.** One background agent per function, each with `isolation: worktree` (the worktree appears under `.claude/worktrees/`, which git ignores). The prompt names the function and points at the skill. Each agent runs `tools/wt_setup.sh` (links `orig/` and `.cache/`), works, and either commits on its branch or stops. Agent commits do not carry `PROGRESS.md`: the hook skips it in a linked worktree.
3. **Land.** As its last step each agent runs `python3 tools/land_self.py` in its worktree. It first waits for its turn in the landing queue (`<git common dir>/land-queue.lock`, shared by all worktrees), printing who holds it, so landings run one at a time and waiting runs use no CPU; it keeps its turn until it lands or stops. Without the queue, each landing moved `mainline` under every other run and made it rebuild, so N agents landing at once cost about N² builds. Then it replays the agent's commits onto the current `mainline` (`tools/rebase_onto_mainline.py`, which uses `apply_commit.py`), runs `make release`, amends a new `PROGRESS.md` into the branch's last commit, then takes a lock (`<git common dir>/land.lock`) and fast-forwards the main checkout's `mainline` to the branch, if `mainline` has not moved since the replay; otherwise (the orchestrator, or a run of an older `land_self.py` without the queue, landed first) it replays again (up to 15 tries). A replay that stops leaves the queue; `rebase_onto_mainline.py --continue` by hand does not queue, since `land_self.py` replays again inside its turn. It waits up to 10 minutes while the main checkout has uncommitted changes. It never forces and never pushes. Exit codes: 0 landed, 1 the replay stopped (the agent fixes it, with its context, and runs it again), 2 `make release` failed, 3 gave up, 4 busy: a replay is open in the worktree (`rebase-onto-mainline.json`), or another `land_self.py` or `rebase_onto_mainline.py` holds the worktree's lock (`<worktree git dir>/land-self.lock`; wait with `flock <file> true`), 5 a commit that changes `src/` or `include/` has no tenets review stamp (`tools/review_stamp.py`; the message names the commits and the steps; `Propagate ...` commits that only add files and `WIP ...` commits that leave `include/` alone are exempt). The check runs before the replay; a replay keeps a commit's stamp even when the merge changes its diff. When the replay changes `tools/land_self.py` or `tools/review_stamp.py`, the run starts again from the replayed copy before it builds (keeping its queue turn), so a run that started with older tools still gets mainline's checks. The mainline lock is separate. `make` and `fn.py` run ninja under `build/.ninja.lock`, so two builds in one checkout wait for each other instead of deleting each other's delinked objects. Keep the main checkout on `mainline` and clean while agents run.
4. **Collect.** Each agent ends with a `RESULT:` block: `matched` with its commit hashes and `LANDED: <mainline hash>`, or `partial`/`skipped` with notes.
5. **Land what is left.** For a matched commit that did not land (exit 3), on `mainline`:
   ```sh
   python3 tools/apply_commit.py <hash>
   ```
   It replays the commit by meaning (delinks entries by address, symbol renames by address and all in one pass, so A → B plus C → A never chain, other symbol and relocation lines added, removed or changed by name and `from:` address, headers as below, source files with a 3-way merge) and commits with the original message; the hooks run `make release` and write `PROGRESS.md`. On a conflict it stops with the changes staged.
6. **After the batch.** Rerun `propagate.py` (new heads pay for their families) and run `permute.py` on each new partial. Record the runs in `tools.txt` and each agent's tokens in `loop-prompts/batchN/log.txt` (`group | matched/attempted | model | tokens | minutes | landed | family members propagated from this agent's heads`). Each batch row below reports model-only and total functions per 1M model tokens.
7. **Clean up.** `git worktree remove` each finished worktree and delete its branch. Partial attempts can be kept for a second pass: note the function and best percentage in the batch log below.

## Shared headers

Agents add fields, typedefs and prototypes to the same headers at the same time. When `git merge-file` cannot merge a header under `include/` (or both sides added the same header), `apply_commit.py` merges it with `tools/header_merge.py`:

- Struct fields are placed by byte offset, computed from their types. Each side is laid out with its own definitions first, since a struct it embeds can have another size on the other side. The result has the named fields of both sides, with the padding written again between them.
- Where both sides name the same bytes differently, mainline's name stays, and the commit's C files are rewritten to it (`->name` and `.name` only). `->name` does not say which struct it reads, so the rewrite happens only when no struct in `include/` still has a field of the old name; otherwise the replay stops and lists the uses (`file:line`) for the agent to change by hand. A struct the commit names differently for the same extern is merged into mainline's struct and renamed the same way.
- Where mainline still has the base version of a field or declaration, the commit's edit wins, as in a 3-way merge.
- Typedefs, structs, `#define`s, externs and prototypes that only one side has are kept; where both changed one, mainline's version stays, except that a `#define` with two different values is a conflict. Enums keep the constants of both sides; the commit's new ones are written with their values (`TERRAIN_SILO = 17,`) so no mainline constant moves, and a constant with two values is a conflict. Fields that overlap without matching are reported as conflicts.
- Anonymous unions and structs are merged member by member, also inside a union. A field named `pad*` is padding and is written again; a bit-field named `pad*` stays.
- Afterwards, local prototypes in the commit's C files are dropped when an included header declares the function; the header's version wins.

Each merged header prints one line (`merged include/game/x.h: +3 fields, ..., renamed a->b`). A "kept mainline's X (the commit has Y)" note means the commit's code may not build until it uses mainline's type; the agent fixes that during its rebase.

## Running on its own

`/decomp-orchestrate` (`.claude/skills/decomp-orchestrate/`) runs the steps above with no one at the keyboard. It keeps its state outside git in `work/loop/` (`state.json` through `tools/loop_state.py`, `journal.md`, `steer.md`), so agents never see it and a new session continues where the last one stopped. A recurring cron job in the session wakes it every 23 minutes, which also brings it back after a usage limit; agent notifications wake it in between. There are no separate phases: the next batch's planner, the partial retries, the renames pass and the wrap-up (tools rerun, batch row, issues, worktree cleanup) are jobs that take agent slots beside the running groups, so slots stay full. `steer.md` holds sturmds's direction for planning and one-off requests; a `PAUSE` line stops new launches. A lease in `state.json` (session ID and process ID) keeps two sessions from running the loop at once.

## Rules for the orchestrator

- Nothing lands unless `make release` passes on `mainline` after the replay.
- Review each landed commit's C against `TENETS.md` before the next batch; fix the skill when the same problem shows up twice.
- Check where each landed file sits ("Source layout" in `CLAUDE.md`). Tell agents which topic directory their group belongs to, and move misplaced files between batches.
- Agents do not edit `tools/`, `docs/`, `Makefile` or `hooks/`. Tool fixes happen on `mainline` between batches.
- Problems from agent feedback that are not fixed right away go into `docs/issues/`.
